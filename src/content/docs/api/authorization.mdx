## The model

- **Users** get powers through [roles](/admin/roles/). A request is allowed
  when the caller's effective permission set satisfies the permission the route
  requires. Roles may also carry server-scoped and node-scoped grants, which are
  merged in for the specific server being touched.
- **API keys** carry their own scopes, chosen at creation, but can never exceed
  their owner's permissions — see
  [Expiry and live permission checks](/api/authentication/#expiry-and-live-permission-checks).
- **Subusers** are granted a subset of the server-scoped permission list by the
  server owner.

## Admin bits

Three permission values have implied meaning:

| Value | Grants |
| --- | --- |
| `*` | Everything (Super Admin). |
| `admin.write` | Every concrete permission, read or write. |
| `admin.read` | Every read permission: anything ending in `.read`, plus `node.view_stats` and `backup.download`. |

A resource-scoped admin bit (`admin.read:<id>`) does **not** widen to all
resources.

### Server-scoped permissions

The grantable set for a specific server — subuser grants and the role wizard's
scoped-access step — is the server permission list returned by
`GET /api/permissions/server`:

`server.read`, `server.start`, `server.stop`, `server.install`,
`server.reinstall`, `server.rebuild`, `server.update`, `server.transfer`,
`server.delete`, `server.schedule`, `console.read`, `console.write`,
`file.read`, `file.write`, `backup.read`, `backup.create`, `backup.restore`,
`backup.delete`, `backup.download`, `database.read`, `database.create`,
`database.rotate`, `database.delete`, `alert.read`, `alert.create`,
`alert.update`, `alert.delete`.

Server owners and full admins implicitly hold the whole set for their servers.

## What to do when you get 403

A `403` with code `PERMISSION_DENIED` means authentication worked but the
identity lacks the permission — not that the endpoint is wrong:

1. Check which identity you sent (session user vs. which API key).
2. Compare its permissions against the endpoint's requirement in the
   [API reference](/api/reference/).
3. Ask an administrator to widen the role/scope, or use a better-scoped key.
   Remember that an API key is also rejected when the owner no longer holds a
   scope the key was granted.

## Design guidance for integrators

- Request the smallest scope that works today; widen deliberately later.
- Distinguish "not found" from "forbidden" carefully in your UX: returning 404
  for things the caller may not see avoids leaking existence — match the API's
  behavior rather than inventing your own.
- Permission names are stable identifiers. Cache the catalog, but re-fetch when
  you see unknown-permission errors after a panel upgrade.
