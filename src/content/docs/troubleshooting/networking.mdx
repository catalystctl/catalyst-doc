## Prerequisites

- A running game server whose allocation you can read from the panel.
- For the node and TLS sections: shell access on the node, and access to the
  install directory to read the `.env` and view proxy logs.

## Players cannot reach a game server

1. Is the server **running**? A stopped server refuses everything.
2. Is the address right — IP **and** port? Retype it; do not trust memory.
   The **Address** column in **Servers** and the server's **Admin** tab show
   its allocations.
3. Is the port reachable from outside? Test from a different network (mobile
   data works). "Works on my LAN, not from outside" means NAT/firewall, not
   the game.
4. **UDP vs TCP**: many games need UDP. A TCP-only port check passing proves
   nothing for a UDP game.
5. Host firewall, cloud security group, and any NAT rule must all agree, and the
   allocation must be published on the node. The node agent creates the port
   mapping and firewall rule for each server allocation; a rule that failed to
   apply looks exactly like a closed firewall.

## Node cannot reach the panel

From the node: resolve the panel hostname, then `curl` the panel URL. Fix DNS
first, then TLS (cert valid for that name?), then HTTP. See
[node issues](/troubleshooting/node/).

## TLS warnings in browsers

- Name mismatch: the certificate must cover exactly the host users type. Set
  `PUBLIC_URL` in the install `.env` to that `https://` URL.
- Expired: renewal failed — port 80 reachable? DNS unchanged? Check the TLS
  overlay's logs (`docker compose logs caddy` or `traefik`), not the backend.
- Mixed setups: after moving TLS to the proxy, `PUBLIC_URL` must still be
  `https://…`.

## SFTP times out

SFTP runs on the **node agent** (default port **2022**), not on the panel, and
is separate from game ports. Confirm the port is written into the agent config
on the node, reachable through every firewall layer, and that the client uses
SFTP (SSH transport), not FTP. Details: [SFTP](/users/sftp/).
